4. Multiinstitución

El sistema debe estar preparado para que una misma instalación gestione varias instituciones.

Ejemplo:

Plataforma
│
├── Universidad Nacional
│   ├── Facultad A
│   ├── Facultad B
│   └── Facultad C
│
├── Universidad B
│   └── Facultad X
│
└── Instituto

Por lo tanto debe existir:

tenant

Cada registro importante debe estar asociado a un tenant_id.

Ejemplo:

users
events
participants
activities
certificates
payments

deben tener relación con la institución correspondiente.

Esto evita que un administrador de una facultad pueda acceder a información de otra.

24. Control de entrada y salida

Ejemplo:

El sistema calcula:

90 minutos
+
75 minutos
=
165 minutos

Actividad:

180 minutos

Porcentaje:

165 / 180 * 100 = 91,67 %

Por lo tanto:

asistencia = 91,67 %

30. Numeración

Debe existir un generador transaccional.

Ejemplo:

UNT-ECO-2026-000001
UNT-ECO-2026-000002
UNT-ECO-2026-000003

Nunca generar el número simplemente con:

COUNT(*) + 1

porque produciría duplicados bajo concurrencia.

Usar:

PostgreSQL sequence

o mecanismo transaccional equivalente.

51. Reglas de negocio

La IA debe implementar reglas explícitas.

RN001

Una persona no puede tener dos inscripciones activas para el mismo evento.

RN002

Una inscripción paga no pasa a CONFIRMED hasta recibir confirmación válida del proveedor de pago.

RN003

Un QR inválido nunca genera asistencia.

RN004

Un participante no puede registrar dos entradas simultáneas para la misma actividad.

RN005

Una salida sin entrada previa debe ser rechazada o registrada como incidencia.

RN006

Un certificado solamente puede emitirse si cumple las reglas configuradas.

RN007

Un certificado revocado nunca debe mostrarse como válido.

RN008

Un evento cerrado no admite nuevas inscripciones salvo autorización administrativa.

RN009

Una actividad no puede superar la capacidad de su sala.

RN010

Los webhooks deben ser idempotentes.

RN011

Toda acción administrativa crítica debe quedar auditada.

RN012

Los datos de distintos tenants nunca deben mezclarse.

83. Instrucción maestra para la IA desarrolladora

Podés utilizar como prompt base algo como esto:

Desarrollar una plataforma web multiinstitucional de gestión integral de eventos académicos utilizando arquitectura modular, API-first y PostgreSQL como base de datos.

La plataforma debe administrar eventos, jornadas, congresos, cursos, talleres y seminarios desde su creación hasta la certificación y validación posterior.

Implementar los módulos de autenticación, usuarios, roles, permisos, instituciones, eventos, tipos de evento, módulos académicos, actividades, salas, docentes, ponentes, materiales, participantes, formularios dinámicos, inscripciones, cupos, listas de espera, pagos, Mercado Pago, credenciales digitales, QR, acreditación, asistencia, evaluaciones, resultados, reglas de certificación, certificados PDF, validación pública mediante QR, revocación, encuestas, notificaciones, email, reportes, exportaciones y auditoría.

Utilizar PostgreSQL con migraciones versionadas, Redis para cache y colas, BullMQ para procesos asíncronos y almacenamiento compatible con S3 para archivos.

El backend debe estar construido como API REST versionada /api/v1, con documentación OpenAPI, validación de DTOs, JWT, refresh tokens, RBAC, rate limiting, auditoría, logs estructurados, idempotencia y controles de seguridad.

El frontend debe consumir exclusivamente la API y no acceder directamente a PostgreSQL.

Separar claramente las entidades Persona, Participante, Evento, Inscripción, Actividad, Asistencia, Evaluación, Resultado y Certificado.

Implementar un motor configurable de reglas de certificación que permita definir requisitos de asistencia, evaluación, actividades obligatorias y módulos obligatorios sin modificar código fuente.

Implementar generación de certificados mediante plantillas HTML/CSS, generación automática de PDF, número único, UUID de validación y código QR. La validación pública debe permitir comprobar la autenticidad del certificado sin autenticación.

Implementar Mercado Pago mediante webhooks y nunca confirmar pagos únicamente por el redirect del navegador. Los webhooks deben ser idempotentes.

Implementar control de cupos utilizando transacciones y bloqueo de filas para evitar sobreasignación concurrente.

Implementar asistencia mediante QR con registro de entrada, salida, actividad, fecha/hora, operador y método de registro.

Implementar WebSocket para actualizar dashboards de asistencia en tiempo real.

Todo cambio administrativo crítico debe registrarse en una tabla de auditoría.

No implementar toda la aplicación en una única iteración. Dividir el desarrollo en fases. Antes de escribir código de cada fase, analizar dependencias, crear o actualizar el modelo de datos, generar migraciones, implementar backend, implementar frontend, crear tests unitarios, integración y E2E y verificar los criterios de aceptación.

No inventar tablas, endpoints o relaciones que contradigan el modelo de dominio existente. Mantener compatibilidad hacia atrás de la API.

Cada módulo debe incluir:

Modelo de datos.
Migraciones.
Entidades.
DTOs.
Servicios.
Controllers.
Guards.
Permisos.
Validaciones.
Endpoints.
Tests.
Componentes frontend.
Estados de carga y error.
Auditoría.
Documentación.

No considerar una funcionalidad terminada hasta que el flujo completo pueda ejecutarse desde frontend hasta base de datos y pueda ser probado mediante tests.

84. Lo que yo agregaría antes de comenzar a programar

Hay tres documentos adicionales que conviene generar antes de pedirle a la IA que escriba código:

Documento A — Modelo ER completo

Con todas las tablas, columnas, tipos PostgreSQL, índices, claves foráneas, restricciones y cardinalidades.

Documento B — Contrato API

Cada endpoint con:

URL
método
autenticación
roles
request
response
errores
validaciones
Documento C — Historias de usuario + criterios de aceptación

Por ejemplo:

Como organizador quiero crear un evento para poder publicar una actividad académica.

Y después:

AC-001
El nombre es obligatorio.


AC-002
La fecha final no puede ser anterior a la inicial.


AC-003
Un evento en estado DRAFT no aparece públicamente.


AC-004
Un evento PUBLISHED puede visualizarse sin autenticación.


AC-005
Un evento REGISTRATION_CLOSED no permite nuevas inscripciones.

Con esos tres documentos, la IA deja de "interpretar" qué querés construir y pasa a tener una especificación prácticamente ejecutable.
